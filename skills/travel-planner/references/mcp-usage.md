# 已部署 MCP 的调用与数据映射

本分享版按高德、社区铁路、滴滴与 RollingGo 酒店定义路由。实际连接、授权与工具名取当前宿主发现结果，发布者机器的可用性不能继承。安装和跨宿主配置见 [Agent 交接](../AGENT_HANDOFF.md) 及 [宿主配置指南](harness-setup.md)。

## 在何时查询

| 决策环节 | 调用顺序 | 查询到什么程度 |
| --- | --- | --- |
| 目的地/方案探索 | 高德搜索候选地点；日期和起点明确后查关键路线；涉及高铁再查铁路；涉及住宿查酒店 | 先少量差异明显的候选，避免为未选方向逐条查价 |
| 交通比较 | 铁路站码→目标日直达→需要时中转；高德查接驳和自驾；滴滴地点→预估 | 比较门到门时间、双人完整费用和驾驶负担，不能只比车上时间 |
| 住宿初筛/选定 | 酒店标签→搜索→少量入围酒店详情；高德另查实际酒店位置与到达路线 | 搜索最低价只做初筛；选定具体房型、套餐、日期与人数后才形成报价证据 |
| 景点与餐饮 | 高德搜索/周边→详情；景区官方页面核验开放、预约、票价、公告 | 按兴趣、顺路程度、步行负担和天气筛选，未知开放规则保留待核实 |
| 详细排程 | 高德连接实际入口、车站、酒店；补必要的铁路/酒店详情与天气 | 算上候车、换乘、取还车及风险缓冲，含缓冲到店早于 22:00 |
| 局部修改/临行复核 | 只重查受改动、时效或冲突影响的地点、路线、票务、房型及天气 | 保留旧证据和版本；不重复扫描所有城市，不创建后台轮询 |

一次只发起一个外部查询；结果已相符时复用其地点 ID、站码和同条件证据。搜索默认约 3 个候选，必要时再扩大；需精确站点后过滤时可多取少量铁路结果，不能把截断后的空集说成没有列车。瞬时网络错误最多重试一次；鉴权、配额、业务拒绝不盲重试。部分服务失败时继续独立可做的工作，并明确缺口。不要为检查可见性而每次把全部服务都查询一遍。

## 高德：地点、路线、天气

- `maps_text_search` 用城市、具体名称查找车站、酒店、景区、餐饮或停车点；`maps_around_search` 只用已返回坐标查周边。对将用于导航/关键排程的候选用 `maps_search_detail` 复核 POI ID、名称、城市、地址及坐标。同名地点或多个入口不能默选第一条；`maps_geo`/`maps_regeocode` 用于地址与坐标核对。
- 从同一高德查询链取得起终点坐标后调用 `maps_direction_driving` / `maps_direction_walking` / `maps_direction_transit_integrated`；公交跨城传 `city`、`cityd`。`maps_distance` 只作相应类型距离比较，不能用直线距离证明道路时间。路线可能返回直接字段或 `route` 包裹，按实际返回解析；缺路径或耗时不是零。
- 参数坐标为 `经度,纬度`，保存坐标来源/体系，不能直接混用第三方酒店或其他地图坐标。距离、耗时保留原单位，在入模时从 m/s 显式转为 km/min，必要时向上取整分钟并说明精度。当前道路耗时是查询快照，未来出行时需缓冲和复核。
- `maps_weather` 只接收城市/adcode，检查返回的具体覆盖日期；未覆盖旅行日时保持天气待复核，不能把“今天”改标签为旅行日。天气不等于灾害预警/景区安全公告。
- 当前白名单不含创建地图、实时定位、叫车或购买门票；不构造未经验证的导航链接。地图里的酒店、充电站、租车点 POI 分别不证明房型库存、实时空闲、租车资格。

## 铁路：直达、中转

先读 [铁路参考日期规则](transport-planning.md#12306-目标日期缺数据时)。用户说今天/明天时先 `get-current-date`，按 Asia/Shanghai 得到明确日期；缺出发地/目标日时不让供应商默认值代替用户条件。

1. 指定车站用 `get-station-code-by-names`，可 `stationNames="光明城|香港西九龙"` 批量查询。用户只给城市时用 `get-stations-code-in-city` 研究可用车站；`get-station-code-of-citys` 是城市代表码，不能替代用户已指定的站。需要核对编码时用 `get-station-by-telecode`。
2. `get-tickets` 明确传 `date/fromStation/toStation`，并按需求传车次类型、出发时段和有限数量；需要结构化核验时用 `format="json"`。**返回可能含同城其他车站**，逐条核对实际起讫站名/码、乘车日期、发到时刻、席别、票价与余票。数量限制可能隐藏精确站点结果；适当扩大一次或说明查询截断，不能把“杭州”结果标成“杭州东”。
3. `start_train_date` / 衍生的 `start_date` 可能是列车从始发站开出的日期，经过夜行后可早于本段乘车日。结合目标查询日、实际乘车站、经停与跨日信息核验；有歧义可用 `get-train-route-stations` 辅助，但不要凭一个字段擅改日期或编造准确到达日。无法消除歧义则不能作确定排程。
4. 用户要中转、直达不合适时调用 `get-interline-tickets`；支持 `middleStation`。自动中转为空时可根据真实铁路站点和路线选择少量合理枢纽串行再查，不固定套用某城市。返回最多前 10 条，空结果只代表本次检索未返回，不是证明全网无中转。
5. 中转逐段核对实际站点、日期、余票、票价；区分同站与跨站换乘，跨站另查高德路线并计缓冲。用明确发到时间计算等待/总历时，不盲信可能格式异常的 `lishi`。当天剩余班次按查询时刻筛选，但还须留到站、安检和边境相关流程的实际缓冲。缺席别价格、规则或换乘证据保持未知。
6. 铁路费用按两张人票计；每段独立报价，往返/中转不漏段、不重复收费。余票是快照，结果不等于已买到票。目标日缺数据的参考查询保留双日期，不能借参考时刻通过酒店/赶车硬约束。

## 滴滴：两人一车的预估

按 [双人合乘规则](transport-planning.md#双人合乘一辆车) 操作。先 `travel_didi.maps_textsearch` 核对起终点及上车区，再用实际返回的经纬度与名称调用 `taxi_estimate`；返回坐标体系不明时不跨地图直接拼接。默认两人合乘一辆车，单程整车费只计一次。该接口不收未来出发日期/人数；Quote 使用 `reference`，保留 `pricing_basis=current_estimate`，不能称未来锁价或保证接单。

## 酒店：搜索与房型复核

1. 先确认城市/住宿区域、入离店日期、人数和房间数。默认两成人、一间大床房、¥200–300/房晚、优先华住；这些偏好可按本次明确需求覆盖。日期未定时只研究区域，不让服务端“明天/1晚”的默认值变成用户旅行日期。
2. 首次需要标签筛选时 `getHotelSearchTags({})` 取得当前有效标签，本会话可复用。`searchHotels` 的 `originQuery` 只归纳住宿需求，不复制聊天/身份/健康资料。明确传 `place`、`placeType`、`checkInParam={checkInDate,stayNights,adultCount:2}`、适用的 `hotelTags` 和 `size:3`。城市形式为“杭州 中国”，车站/景点等补齐所属城市。按返回标签选大床，`preferredBrands` 可为汉庭/全季/桔子，`maxPricePerNight` 默认 300。¥200 是偏好区间下沿，不因舒适酒店低于 ¥200 就硬过滤。
3. 返回酒店 ID、名称、区域和搜索价后先筛选；预算/品牌未命中时说明取舍，不能静默放宽用户硬要求。用高德重新检索候选酒店并核对地址、分店，路线使用高德自己的坐标；不要把 RollingGo 经纬度直接当作高德坐标。分页只在用户要更多或候选不足时使用 `nextPageToken`；条件变化重新首页查询，不沿用旧 Token。
4. 对少量入围酒店调用 `getHotelDetail`，优先用搜索真实返回的 `hotelId`，显式传 `dateParam={checkInDate,checkOutDate}` 与 `occupancyParam={adultCount:2,childCount:0,roomCount:1}`。核对响应 ID、日期、人数、房数、房型、大床/双床、可住人数、套餐、早餐份数、货币、价税口径、强制费用、取消截止及可售状态；字段缺失不能凭搜索标签补齐。无明确取消截止/时区时不能承诺“到某时免费取消”。
5. `isOnRequest=true` 表示仍需申请/确认，不能当作已确认即时可售；false 也不保证未来库存。搜索最低价不是所选房型价；最低单晚价、平均每晚价、全程价、押金、税费必须区分。套餐价要对应实际晚数和一间房，禁止把双人住宿费用再乘二。第三方“华住”套餐名不能证明用户华住会员价。
6. 按实际完整房期计算房费：Quote 的 `unit=room_night`、`quantity=rooms×nights`。逐晚价格不同或全程总价不能精确整除房晚数时，以 `unit_amount_minor=null` 和带来源的完整房期金额 component 记录已知小计，保留原价明细，不四舍五入伪造统一单晚价；未知税费时 `mandatory_fees_complete=false`。库存待确认或仅搜索展示价用 `reference`，不能升级为完整已核实报价。
7. `policies_verified` 只在房型、双人入住、最晚到店与退改均有相符来源时为 true。缺最晚到店保留 null/待核实；酒店允许晚到也不豁免本 Skill 的早于 22:00 规则。酒店政策、价格和用户是否预订独立；查询不创建 booking，也不调用锁价、下单、支付或取消工具。

## 景点与餐饮：位置、规则和商品分开

当前无已启用的景点票务 MCP。美团停用，不作隐式兜底；不为一次规划自动安装新服务。

- 用高德找地点及邻近餐饮，结合用户偏好比较自然/街区/文化等体验、顺路程度、步行 5–10km 的软偏好和酒店到达时间。游览时长、拥挤程度等推断标为估计，并给雨天或关闭备选。
- 用原生网页搜索/浏览器查景区官网、官方预约渠道/公告：目标日营业、最后入园、预约名额、临时关闭、入场规则、实际票种/年龄/日期/价格和退改。地图营业字段或游记可作线索，关键规则优先最新官方证据；冲突保留来源和待核实项，不能挑一个有利值通过校验。
- 景区、实际入口/停车点和收费项目/门票套餐分开关联。进景区的路线连到实际可用入口；中心点不自动当入口。门票产品价格不自动代表整个景区费用，平台没票不等于闭园，网上“免费”也不等于无需预约。
- 现有模型用不同 Place ID 区分入口等地点，Activity 表示参观安排，Quote 表示票种费用；票种 ID/套餐/入口关系写 `SourceRecord.conditions` 和实体 `notes`，不要往严格 Schema 添加临时字段。`access` 未核实用 unknown；需要预约而未取得可靠预约确认时 `reservation_verified=false`，不能把“允许预约”当作用户已预约成功。用户可以选方向，详细确认仍遵守硬约束校验。

## 将查询结果交给本地核心

Python CLI 负责保存/预算/校验，真实 MCP 由当前 agent/宿主编排；`travel.py query` 的 ProvidedDataAdapter 不是实时供应商客户端。不要先设 mock/user_provided 再改标签冒充 live。

| 目标 | 映射与证据要求 |
| --- | --- |
| SourceRecord | provider 包含服务/工具标识，queried_at 为含时区实际查询时间；conditions 保留匿名输入、实际站码/POI/房型/票种 ID、适用日期/人数/单位/坐标体系；note 区分核验、估算及缺口。url 用真实公开来源链接或 null，绝不存带 Key 的连接地址 |
| 来源等级 | 高德官方接口可用 kind=official；RollingGo、滴滴及社区铁路封装用 provider，记录实际上游来源；铁路参考日、当前车价等仅参考证据用 reference。reliable 依字段和条件核验，不凭供应商名设 true |
| Route / Transport | 保存真实起讫点、含偏移量时刻、换算距离/耗时与 source_ids；缺耗时保持 null/evidence=unknown，估算为 estimated。对不同交通候选分别关联，避免一段费用重复进入预算 |
| Accommodation / Quote | 酒店 ID/房型/套餐细节放来源 conditions；金额以货币最小单位整型保存。conditions 是实际查询条件，expected_conditions 是本次期望条件，不能同步改成错误值来制造匹配。valid_until 没有实际依据用 null，不编造锁价时效 |
| Activity / Quote | 开放和预约证据与票价分别关联；免费、付费、未知分开。推荐理由/估计时长/入口关系放 notes，保留官方规则的日期和来源 |

实际费用仍以用户确认/订单为准。保存后运行 `validate` 检查 sources 引用、日期/条件、预算范围与三态硬约束。响应“success”仅代表接口层成功，不代表上述业务核验通过。
