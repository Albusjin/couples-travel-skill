# Travel Planner Skill — 软件需求规格说明书

**版本：V1.0**

**状态：需求基线已确定，外部工具可行性待验证**

**目标平台：Codex Desktop**

**适用范围：中国大陆情侣双人自由行**

**文档日期：2026-11-01**

---

## 1. 产品概述

### 1.1 产品定位

Travel Planner 是运行在 Codex 中的个性化旅游规划 Skill。

它通过读取用户确认过的长期旅行偏好、理解单次旅行需求、研究和比较可行方案、生成结构化行程、管理旅行状态，实现从旅行构想到出行准备及旅途中调整的完整规划流程。

产品重点服务情侣双人旅行，关注性价比、住宿舒适度、小众景点、路线合理性、自驾与租车体验，以及自由灵活的游玩节奏。

### 1.2 核心目标

- 能根据模糊需求推荐目的地，也能对指定目的地进行详细规划。
- 对高铁、全程自驾、高铁后租车等方式进行完整成本与时间比较。
- 按双人出行偏好推荐酒店、自动挡租车车型、景点和餐饮。
- 形成真实、合理、可核验的每日路线，避免明显时间冲突。
- 保留已确认和已预订的安排，支持局部修改与版本追踪。
- 从同一旅行数据生成详细攻略、地图导航、预算表及按需导出的文档。
- 为未来私有移动端网站和行程同步提供结构化数据基础。

### 1.3 V1.0 非目标

第一版不要求实现：

- 自动提交高铁、酒店、租车或景区订单。
- 自动支付、取消订单或修改第三方平台订单。
- 24 小时持续运行的价格和交通监控。
- 实时车辆位置追踪。
- 对所有旅游供应商的实时库存提供保证。
- 两个人同时从网页编辑同一份计划。
- 医疗诊断、健康预测或自动生理周期追踪。

这些能力属于后续扩展，需要独立验证其技术可行性、账号权限与数据来源。

## 2. 需求确认与约束级别

所有要求应明确归为三类。

**硬性约束（Hard Constraint）：** 默认不得违反。违反时应阻止方案直接确认，并说明冲突。

**软性偏好（Soft Preference）：** 尽量满足。存在更好备选时可以提出，但必须说明取舍。

**单次条件（Trip Override）：** 只影响当前旅行。若与长期软性偏好冲突，以本次明确要求为准；若涉及安全或其他硬性约束，应要求确认调整，不得静默覆盖。

### 2.2 尚未确认的设计假设

以下不应被误认为用户已经同意的长期偏好。

| 假设 | 建议默认做法 |
|---|---|
| 候选方案数量 | 一般展示 2–3 个，复杂情况适当增加 |
| 行程缓冲 | 根据交通和不确定性动态分配，而非固定分钟数 |
| 自由活动比例 | 每天适当留白，具体时长根据景点和路线调整 |
| 租车预算 | 每次根据总预算、日期、城市和车型重新确定 |
| 租车动力类型 | 燃油、纯电、插混按实际情况比较 |
| 出行装备 | 按季节、活动、天气、行李容量推荐 |
| 酒店早餐与停车 | 作为比较指标，暂不设为必须条件 |
| 高铁座席偏好 | 需在具体旅行中确认 |
| 两人行程是否允许分开活动 | 尚未确定 |
| 网站登录与身份验证方式 | 在网站实施阶段确定 |
| 网站同步触发方式 | 初期建议用户确认后发布 |

设计假设可以用于生成候选方案，但不能直接写入长期偏好。

## 3. 输入契约

### 3.1 支持的输入方式

系统必须支持自然语言输入，不强制用户每次填写固定表单。

支持三种模式：

**A. 探索型输入**

用户只说明时间、出发地、预算和大致偏好，Skill 推荐目的地及候选路线。

**B. 指定型输入**

用户已经有明确目的地，Skill 直接研究交通、住宿、租车及每日活动。

**C. 修改型输入**

用户引用已有旅行，要求调整日期、交通、酒店、景点、预算或当天路线。

### 3.2 基础字段

| 字段 | 类型 | 规则 |
|---|---|---|
| `origin` | 地点 | 必需；缺失时询问 |
| `destinations` | 地点数组 | 可为空；为空时进行目的地推荐 |
| `date_window` | 日期或区间 | 必需；允许模糊日期 |
| `duration_days` | 整数 | 可由日期推导 |
| `travelers` | 旅行者数组 | 默认 2 人 |
| `budget` | 金额对象 | 缺失时可先探索预算区间 |
| `transport_preferences` | 枚举数组 | 默认重点比较高铁、自驾及租车 |
| `interests` | 标签数组 | 从长期偏好及本次输入取得 |
| `must_visit` | 地点数组 | 用户指定的必去地点 |
| `excluded_places` | 地点数组 | 用户明确不想去的地点 |
| `existing_bookings` | 预订引用数组 | 有则加入约束 |
| `special_requirements` | 条件数组 | 只用于本次旅行 |

### 3.3 条件必需字段

只有当相关功能被启用时，才要求补充信息。

- 自驾：车辆类型、出发位置及必要的能耗或续航数据。
- 租车：取还车地点、时间、驾驶员数量、变速箱要求。
- 新能源路线：车型、续航、当前或预计出发电量、充电兼容条件。
- 高铁方案：车站偏好、必要的出发或抵达时间限制。
- 已有预订：订单对应的日期、时段、地点及退改约束。
- 特殊活动：徒步路线强度、海边是否下水等必要信息。

### 3.4 追问规则

FR-IN-01：优先从当前消息与确认的旅行偏好中提取信息。

FR-IN-02：只追问影响当前决策的关键缺失项。

FR-IN-03：对不重要的未知信息允许保留空值并继续研究。

FR-IN-04：不能凭空推断出发城市、真实预订状态、驾驶资质或敏感身体状况。

FR-IN-05：本次旅行的明确要求覆盖长期软性偏好，但不自动修改长期偏好文件。

FR-IN-06：日期表达必须解析为明确日期或待确认日期范围，不能把“下周末”永久保存为相对日期。

## 4. 功能需求清单

### 4.1 需求理解与目的地推荐（P0）

FR-101：根据旅行人数、日期、预算、季节、偏好和出发地推荐目的地。

FR-102：区分经典景点、小众景点、自然景观、海边、徒步和城市休闲等类型。

FR-103：明确每个目的地的推荐理由、交通便利性、预计游玩天数和潜在风险。

FR-104：在用户明确目的地时，不强行重新推荐无关城市。

FR-105：支持用户指定必去景点、排除景点或调整目的地范围。

### 4.2 方案研究与比较（P0）

FR-201：默认构建差异明确的候选方案。

FR-202：综合比较双人总费用、门到门交通时间、驾驶负担、游玩体验、住宿舒适度和路线效率。

FR-203：区分已经查询验证的数据与假设条件。

FR-204：提出推荐方案，同时保留其他方案的主要优劣势。

FR-205：用户选定方向后，才进行更深入的每日规划。

### 4.3 高铁与综合交通（P0）

FR-301：支持高铁与全程自驾、高铁后租车等组合。

FR-302：计算门到门交通时间，而非仅计算高铁运行时长。

FR-303：考虑到站、候车、取车、还车、换乘、行李及必要缓冲。

FR-304：票价、班次和余票未验证时明确标注，不编造实时数据。

FR-305：提供来源可追溯的查询或预订入口（如可取得）。

### 4.4 租车与自驾（P0）

FR-401：只推荐自动挡车辆。

FR-402：根据双人、行李、路况、预算和驾驶距离推荐车型级别。

FR-403：比较基础租金、保险、服务费、异地还车费、里程限制、油费或电费、高速费及停车费。

FR-404：识别两名驾驶人的登记与资格核验要求。

FR-405：核对异地还车是否支持，以及对应地点、时间与附加费用。

FR-406：识别燃油、纯电、插混及增程车型的成本和补能差异。

FR-407：判断路线是否合理，规划停车、加油或充电及休息点。

FR-408：夜间驾驶允许，但路线必须满足每天 22:00 前抵达酒店。

FR-409：车辆交付可能是“同组车型”时，不保证具体型号或配置。

### 4.5 酒店规划（P0）

FR-501：默认两人入住一间双人大床房。

FR-502：优先筛选每晚 ¥200–300 的住宿。

FR-503：华住会优先；在价格、质量或位置明显更合适时允许推荐其他品牌。

FR-504：比较实际房型、卫生、舒适度、位置、隔音、停车、早餐、退改及完整费用。

FR-505：酒店位置必须纳入每日路线优化。

FR-506：检查最晚到店时间、入住政策和预计抵达时间。

FR-507：当 ¥300 以内没有合适酒店时，提供高价备选及选择理由。

### 4.6 景点、美食与每日路线（P0）

FR-601：按地理位置、开放时间、游览时长和活动强度安排路线。

FR-602：优先推荐小众及深度体验项目，但不得编造其实际开放情况。

FR-603：常规每日步行目标为 5–10 公里，特殊徒步单独评估。

FR-604：安排顺路的当地特色餐饮，并保留合理用餐与休息时间。

FR-605：关键交通、预订和入住时段精确；普通活动采用弹性时间段。

FR-606：规划必要的停车、充电、加油、排队及转场时间。

FR-607：不得安排与已锁定项目冲突的路线。

FR-608：每日路线应包含可打开的导航入口；无法核实实际路径时不得伪装为已验证路线。

FR-609：每天必须安排到酒店的返程，预计抵达时间早于 22:00，并留有适当风险缓冲。

### 4.7 预算管理（P0）

FR-701：区分两人合计与人均费用。

FR-702：酒店按房间和房晚计算，不能错误乘以两人。

FR-703：租车按照实际租赁时间和费用规则计算。

FR-704：区分已核实报价、估算、待核实费用和已支付金额。

FR-705：可退押金与预授权单独列示，不计作已发生消费。

FR-706：超过预算时指出主要成本来源，并给出替代方案。

FR-707：未知费用不按零元计算。

### 4.8 确认、锁定与重规划（P0）

FR-801：分别记录候选方案、用户选择、已预订和已完成事项。

FR-802：用户明确确认后，关键决定进入锁定状态。

FR-803：修改行程时先分析受影响对象和依赖关系。

FR-804：优先局部修改，避免重写整个旅程。

FR-805：如需变更锁定项目，先解释后果并获得确认。

FR-806：保留旧版本、修改原因、预算差异及受影响项目。

FR-807：修改成功后保持路线、预算和行程数据的一致性。

### 4.9 旅行装备与个性化关怀（P1）

FR-901：根据天气、季节、目的地、活动和行李条件推荐装备。

FR-902：区分必须、建议、可选和出发前确认项目。

FR-903：支持徒步、登山、海边和普通城市旅行的专项装备。

FR-904：用户主动提到身体或健康注意事项时，提供适当活动调整建议。

FR-905：不自动推测或跟踪生理周期，也不把个人饮食选择误当医学禁忌。

FR-906：敏感健康信息默认不写入长期旅行档案。

### 4.10 文档输出（P0 基础 / P1 扩展）

FR-1001：V1.0 提供 Codex 可阅读的完整攻略。

FR-1002：输出交通、酒店、租车及预算比较表。

FR-1003：输出每日路线及对应导航入口。

FR-1004：所有输出引用同一版本的旅行数据。

FR-1005：Word、PDF、手机版及装备清单在对应功能实现后按需生成。

FR-1006：每份导出文件标注生成日期、计划版本和未核实事项。

## 5. 输出契约

### 5.1 第一阶段：候选方案报告

必须包含：

1. 本次旅行需求概览。
2. 已确认条件与待确认条件。
3. 候选方案对比。
4. 交通方式与主要费用差异。
5. 主要住宿区域与景点组合。
6. 推荐理由、缺点及风险。
7. 需要用户决定的具体事项。

此阶段不要求输出最终详细的每小时行程。

### 5.2 第二阶段：详细旅行计划

必须包含：

- 旅行总体概览。
- 已选择交通和住宿安排。
- 每日时间表及自由活动时间。
- 景点、用餐和休息安排。
- 每一段交通方式、预计时间及导航入口。
- 酒店、停车、取还车、加油或补能信息。
- 天气相关风险和可行替代活动。
- 双人费用明细与未核实价格。
- 预约及预订清单。
- 待确认事项。

### 5.3 第三阶段：执行版输出

旅途中使用的简明版应突出：

- 今天的路线和当前下一站。
- 关键时间限制。
- 地图导航。
- 已预订信息及待确认项目。
- 停车、补能、用餐与休息。
- 当天预算与必要提醒。
- 当前计划版本。

不应把完整研究报告原样复制到手机界面。

### 5.4 输出一致性

所有输出都必须引用同一份旅行主数据及版本。

如果行程更新，旧文件仍可保存为历史版本，但不能标记成最新版。

## 6. 数据模型

### 6.1 设计原则

采用“结构化旅行主数据 + 多种输出视图”的设计。

长期偏好和单次旅行数据分离；报价、预订与支出分离；行程活动、路线和数据来源使用稳定 ID 关联。

### 6.2 核心实体

| 实体 | 关键字段 |
|---|---|
| `TravelProfile` | profile_id、共同偏好、个人非敏感偏好、版本、更新时间 |
| `Traveler` | traveler_id、角色、活动偏好、驾驶偏好 |
| `Trip` | trip_id、schema_version、revision、状态、日期、预算、时区 |
| `TripRequest` | 出发地、目的地、日期范围、硬约束、软偏好、本次覆盖条件 |
| `Proposal` | proposal_id、方案内容、比较指标、状态、风险 |
| `TransportOption` | mode、起终点、出发与到达时间、费用、来源 |
| `VehiclePlan` | 车型级别、变速箱、动力类型、驾驶员、租期、限制、成本 |
| `EnergyStop` | 补能点、预计抵达电量或油量、服务状态、备用方案 |
| `AccommodationOption` | hotel_id、房型、人数、价格、位置、停车、退改 |
| `ItineraryDay` | 日期、活动、路线、当日预算、固定事项、风险 |
| `Activity` | activity_id、地点、时间范围、状态、优先级、锁定标记 |
| `RouteSegment` | 起终点、交通方式、距离、耗时、地图链接、来源 |
| `Quote` | quote_id、金额、计价单位、费用构成、状态、查询时间 |
| `Booking` | booking_id、关联对象、预订状态、退改约束、确认来源 |
| `Expense` | expense_id、金额、状态、支付时间、费用归属 |
| `SourceRecord` | source_id、来源、查询时间、适用条件、可靠性 |
| `Decision` | decision_id、确认人、确认内容、时间 |
| `ChangeSet` | change_id、原版本、新版本、修改内容、影响 |
| `Publication` | publication_id、版本、发布状态、访问权限 |
| `PackingItem` | 物品、分类、重要性、是否已准备 |

### 6.3 数据类型约束

- 所有金额明确币种和计价单位，计算时优先使用整数最小货币单位，避免浮点误差。
- 日期使用明确的年月日，时间包含时区；国内旅行默认使用中国标准时间，但不能省略时间语义。
- 起终点采用可识别的地点标识，必要时记录地理坐标。
- 路线距离、步行距离和车程分别记录，不能混用直线距离。
- 所有报价与预订对象通过 ID 关联。
- 缺失值必须表示为未知或待核实，不能伪造默认价格或库存。
- 数据模型必须有 `schema_version`，旅行计划必须有独立的 `revision`。
- 历史版本、预订变更与支付记录不得被直接覆盖。

### 6.4 长期偏好与单次旅行

长期偏好只包含经过确认、预计长期适用的内容。

每次创建新旅行时生成 `preferences_snapshot`，记录当时使用的偏好版本。

临时偏好仅用于本次旅行，不自动影响其他旅行。

### 6.5 敏感数据隔离

健康与身体相关的临时注意事项不进入可发布旅行主数据。

任何必要的临时活动调整应尽量只保留非敏感的操作结果，例如“当天减少高强度徒步”，而非详细健康背景。

身份证号、驾驶证号、支付信息、账户密码、认证令牌和完整敏感订单凭证不得存储在普通旅行数据中。

## 7. 状态机

### 7.1 旅行状态

建议采用以下基本状态序列：

`draft → researching → proposals_ready → selected → detailed → confirmed → in_progress → completed`

同时允许受控的取消、重新研究和修订流程。

- `draft`：初始需求草案。
- `researching`：正在收集和核验规划信息。
- `proposals_ready`：候选方案可以比较。
- `selected`：用户已选定规划方向。
- `detailed`：详细行程已生成，尚未全部确认。
- `confirmed`：用户认可当前旅行计划版本。
- `in_progress`：旅行已开始。
- `completed`：旅行结束。
- `cancelled`：旅行计划取消，历史保留。

旅行状态与外部订单状态必须独立。

### 7.2 报价状态

`unknown / queried / rechecked / reference / expired / unavailable`

这里的 `queried` 只表示取得报价结果，不代表库存或最终交易价必然有效。

报价有效性必须与对应日期、人数、房型、车型、费用条件和来源相匹配。

### 7.3 预订状态

`not_booked / booking_pending / booked / change_pending / cancelled / completed`

只有用户提供可靠确认或获得可信的订单结果后，才能进入 `booked`。

### 7.4 锁定规则

锁定是独立属性，不应直接与“已预订”混同。

- 已完成的历史活动不得被修改为从未发生。
- 已预订的交通和住宿默认锁定。
- 用户明确确认的关键事项默认锁定。
- 修改锁定项目必须先说明影响并获得确认。
- 无法自动取消的第三方订单不得被标记为已取消。

### 7.5 行程变更事务

每次重规划应执行以下流程：

1. 读取当前有效版本。
2. 识别用户希望修改的对象。
3. 获取相关锁定状态及依赖关系。
4. 构建候选变更。
5. 校验时间、路线、预算和预订冲突。
6. 提示重大变化并获取必要确认。
7. 保存新版本与变更记录。
8. 更新相关派生输出。
9. 若有已发布网站，标记新版本待发布或执行已授权的发布流程。

当校验失败时，不得用不完整的新版本覆盖原计划。

## 8. 硬性约束与冲突处理

### 8.1 酒店抵达时间

CON-001：允许夜间驾驶，但当天预计抵达酒店时间必须早于 22:00。

CON-002：规划时应为停车、还车、充电、吃饭、道路拥堵及其他不确定性留出合理缓冲。

CON-003：不能仅以理想道路耗时作为抵达时间依据。

CON-004：预计无法满足抵达时间时，应主动提供提前结束景点、调整顺序、更换住宿点或缩短驾驶距离等方案。

CON-005：没有可核实交通时间时，不能断言路线满足 22:00 要求。

CON-006：如果用户希望临时放宽规则，必须由用户明确确认；不得静默降低该约束。

### 8.2 自驾安全

- 不推荐明确不适合实际车辆的道路。
- 对山区、夜间、极端天气、长距离驾驶进行风险检查。
- 规划驾驶休息与补能，不能因为有两名驾驶人就忽略疲劳。
- 充电站信息不完整时保留备用方案，并明确出发前核验需求。

### 8.3 景点可进入性

- 核实开放、预约、最后入园及季节性限制。
- 未取得预约信息时标为待核实。
- 不能以未经验证的开放时间计算确定行程。

### 8.4 偏好冲突优先级

默认规则：

**安全与合法性 → 已预订及已确认约束 → 用户本次硬性要求 → 预算与时间目标 → 长期软性偏好 → 一般推荐排序。**

对于同一级别的冲突，提供备选方案，由用户决定。

## 9. 价格与证据管理

### 9.1 证据等级

系统必须区分：

- 本次旅行条件下已查询的报价。
- 临近决策重新核对的报价。
- 只用于参考的历史或一般价格。
- 尚无法验证的价格与库存。
- 已过期或不适用的信息。

### 9.2 价格缺失时的行为

用户已确认：**继续规划，明确标记待核实。**

因此：

- 不能因为酒店房价未知而停止所有景点规划。
- 可以继续生成路线、区域和候选酒店建议。
- 不得把未知费用计为零。
- 不得宣称含未知费用的总预算已经完整核实。
- 需要预订的事项应进入待核实清单。
- 用户准备实际预订时，应重新核验对应价格和库存。

### 9.3 完整费用

必须包含适用的强制费用，并分别列示：

- 交通票价与到站交通。
- 租车基础费用、保障、服务费及异地还车费用。
- 燃油、充电、高速与停车。
- 酒店完整房价和适用费用。
- 景点门票与必要预约费用。
- 餐饮及其他活动。
- 弹性预算。
- 押金和预授权等不属于最终消费的暂时资金占用。

### 9.4 来源记录

对于关键价格、车次、路线、营业时间及场所规则，记录数据提供者、查询时间、适用条件及可用的原始入口。

未验证的外部信息不得标记为实时事实。

## 10. 隐私与权限

### 10.1 本地使用权限

V1.0 默认通过 Codex 在用户授权的本地工作目录内管理旅行文件。

Skill 不应拥有无边界的文件删除、敏感凭证读取或自动对外发布行为。

### 10.2 长期偏好更新

每次更新前展示：

- 拟新增或修改的偏好。
- 原有值和新值。
- 是否属于长期规则。
- 对后续旅行的潜在影响。

只有获得明确确认后才写入。

### 10.3 订单和支付

第一版允许搜索、比较、提供可靠入口及维护手工确认的订单状态。

不得自动付款、取消、改签或提交订单。

后续即使实现交易能力，也必须为每次有实际费用或不可逆影响的操作取得明确授权。

### 10.4 健康隐私

健康关怀仅在用户主动提出时启用。

不预测生理周期、不主动获取伴侣健康资料、不长期保存敏感健康信息。

提供活动和装备建议时尊重当事人意愿，不作医学诊断或强制限制。

### 10.5 未来私有网站

网站必须具备：

- 仅两名获授权用户可访问的身份验证。
- 安全连接。
- 服务端访问控制。
- 不公开旅行日期、住宿及具体行程的搜索索引或公共接口。
- 安全的会话与密钥管理。
- 备份、恢复和删除机制。
- 发布版本及同步状态展示。
- 不将敏感健康资料和证件信息上传至网站。

初始版本以私有只读展示为主。

## 11. 非功能性要求

### NFR-01 正确性

相同输入和同一组数据应产生内部一致的预算、路线、状态和文件引用。

### NFR-02 可追溯性

影响决策的重要外部事实应有来源、适用条件与查询时间。

### NFR-03 可维护性

偏好、规划规则、数据结构和输出模板应分离，便于独立修改。

### NFR-04 可恢复性

任何重大修改不得直接覆盖唯一有效历史版本。

### NFR-05 可扩展性

增加数据工具、输出格式或目的地类型时，应尽量复用既有实体和流程。

### NFR-06 可用性

用户可以用自然语言启动、修改和恢复旅行，而不必学习 JSON 或配置语法。

### NFR-07 失败透明性

当数据不可用、工具调用失败、价格过期或路线无法核实时，应提示问题，并继续完成不依赖该信息的工作。

### NFR-08 最小权限

默认只读外部服务；文件修改、发布和未来交易操作按影响程度申请相应授权。

### NFR-09 时间与地区

明确日期、时区、跨日交通以及最晚入住和返程时间。

### NFR-10 数据迁移

模型结构升级时，能够识别旧的 `schema_version`，进行校验或受控迁移，而不是直接丢弃旧旅行记录。

## 12. 验收测试规范

| 编号 | 测试场景 | 通过条件 |
|---|---|---|
| AC-01 | 未提供出发地 | 主动询问，不擅自确定 |
| AC-02 | 未确定目的地 | 根据偏好推荐可比较方案 |
| AC-03 | 固定日期 | 正确使用指定日期，不更改 |
| AC-04 | 灵活日期 | 支持比较不同日期组合 |
| AC-05 | 双人订房 | 按一间大床房和实际晚数计费 |
| AC-06 | 酒店超过 ¥300 | 可推荐备选，明确解释超出原因 |
| AC-07 | 非华住酒店更合适 | 能作为备选，说明相较华住的优势 |
| AC-08 | 租车平台含手动挡 | 不把手动挡列为符合要求的推荐 |
| AC-09 | 两名驾驶员 | 检查额外驾驶员限制与费用 |
| AC-10 | 异地还车 | 检查可用性、门店条件和额外费用 |
| AC-11 | 全程自驾与高铁租车比较 | 比较完整费用与门到门时间 |
| AC-12 | 新能源长途旅行 | 结合续航和补能安全余量提出路线 |
| AC-13 | 当天预计 22:30 抵达酒店 | 标记违反约束，提出调整而非直接通过 |
| AC-14 | 景点关闭或预约失败 | 提供替代活动，不把不可进入景点当作已确认 |
| AC-15 | 每天步行明显超出偏好 | 标记偏差，并说明替代安排 |
| AC-16 | 酒店实时价格未知 | 继续规划，但标明待核实 |
| AC-17 | 报价缺少必要费用 | 不宣称其为可比完整总价 |
| AC-18 | 用户选定酒店但未预订 | 记录为已选择，而非已预订 |
| AC-19 | 已预订返程车票 | 重新规划不得静默更改 |
| AC-20 | 修改第二天路线 | 第一、三天及锁定内容保持不变 |
| AC-21 | 修改路线后 | 相应更新交通时间、预算与地图数据 |
| AC-22 | 本次临时选择 SUV | 不自动写入长期车型偏好 |
| AC-23 | 请求更新长期偏好 | 经确认才保存，并记录变更 |
| AC-24 | 主动提出健康注意事项 | 只按当次需求调整，不默认长期保存 |
| AC-25 | 导出文件 | 标注旅行版本与生成时间 |
| AC-26 | 外部工具失败 | 明确提示缺失数据，不捏造结果 |
| AC-27 | 新旧版本比较 | 能说明修改内容及相关费用差异 |
| AC-28 | 私有网站扩展 | 未授权用户无法访问已发布计划 |

**验收需区分两个层面：**

一是 Skill 的规划逻辑是否正确；二是外部数据源是否实际提供了所需数据。

例如没有真实酒店报价能力时，可以通过模拟数据验证报价处理逻辑，但不能据此宣布“实时酒店查询功能已经通过验收”。

## 14. 真实工具能力验证清单

本阶段只确定能力要求，不选择任何具体 MCP 或服务。

| 能力领域 | 需要验证的数据与操作 |
|---|---|
| 地图与路线 | 地点检索、可识别位置、路线距离、交通耗时、实际导航入口 |
| 铁路 | 站点、车次、时刻、价格、余票、适用日期和查询时间 |
| 酒店 | 大床房、双人入住、实际日期价格、停车、取消政策与位置 |
| 租车 | 自动挡车型、取还车、两名驾驶人、异地还车及完整费用 |
| 能源补给 | 加油站、充电站、兼容性、可用性、绕行和备用点 |
| 景点 | 开放时间、门票、预约、限制、位置及官方入口 |
| 天气 | 指定地点和日期的预报、天气风险及数据时间 |
| 导出 | 结构化数据生成 Markdown、Word、PDF 和简明版 |
| 数据持久化 | 文件读写、版本校验、历史保存与恢复 |
| 移动发布 | 私有访问、数据同步、版本发布与错误恢复 |

每项能力在工具验证阶段应记录：

- 是否实际支持。
- 是否需要付费或独立授权。
- 是否具有合法可靠的数据来源。
- 是否能提供真实查询结果。
- 数据更新频率、时效性与覆盖范围。
- 是否可在 Codex 当前环境调用。
- 是否存在账户、交易或安全限制。
- 不可用时的降级策略。

**不允许以“某工具名称看上去支持某功能”作为通过验证的依据。**

## 15. 待实施阶段确认的事项

以下事项不妨碍 V1.0 需求基线确定，但需要在实现或真实旅行前处理。

1. **路线缓冲策略**：根据道路、时段和风险设置动态缓冲，具体参数通过测试校准。
2. **驾驶时间建议**：每日驾驶总量根据场景评估，不预设无限驾驶能力。
3. **租车详细参数**：具体动力、车辆规格、保险、租金与驾驶资质按每次旅行决定。
4. **酒店特殊要求**：早餐、停车、禁烟、有窗等条件按本次需求或后续确认的长期偏好决定。
5. **两人分开活动规则**：未来如出现不同兴趣需求，再确定是否支持分开路线。
6. **地图交互形式**：以真实工具能力为基础验证导航链接、路线数据和后续移动端展示形式。
7. **网站发布机制**：确定私有登录、存储、同步、权限和部署细节。
8. **文档模板细节**：Word/PDF 的具体视觉设计、字体、分页、地图展现形式。
9. **报价完整性**：不同供应商的价格、退款政策和库存是否足以进行公平比较。
10. **数据源能力边界**：每项功能的自动查询范围需以真实工具测试结果为准。

## 16. 需求冻结结论

Travel Planner Skill V1.0 的产品定位、目标用户、核心功能、输入输出契约、基本数据模型、状态机、权限边界及验收标准已经确定，可以作为后续详细设计和实现的基线。

需求冻结并不意味着所有外部数据和工具能力已经得到验证。

实现阶段必须保证：

**第一，所有关键规划结论可解释、可核验。**

**第二，用户对重要选择、长期偏好修改及任何外部交易保有最终控制权。**

**第三，旅行数据具有明确状态与版本，不因局部修改产生不一致。**

**第四，安全、合法性和已经确认的硬性约束优先于预算、效率及旅行体验。**

**第五，系统在工具或数据缺失时能够透明降级，而不是编造完整结果。**

本规格作为 Travel Planner Skill V1.0 的正式需求基线，后续修改应通过版本记录管理，而不是在实现过程中静默改变已确认规则。
