# V1.0 实施补充与待决事项

> 配套文件：[软件需求规格说明书 V1.0](Travel-Planner-PRD-v1.0.md)。本文件是实现建议与待决问题，不改变已冻结的需求，也不代表外部工具或功能已经实现。若与正式规格有冲突，以正式规格和用户后续明确决定为准。

## 1. 建议的实施顺序

1. **规则和输入**：实现自然语言输入、缺失项追问，以及已确认默认值、单次覆盖和硬约束的区分。保存偏好之前逐项请求确认。
2. **旅行主数据**：定义带 `schema_version` 与 `revision` 的最小结构，分离偏好、单次行程、来源、报价、预订和支出；先使用不含真实个人信息的样例验证。
3. **候选和细化**：先比较方案，再按选中方向细化；对缺失价格、路线和营业信息分别标注，保留不依赖缺失数据的规划。
4. **约束校验**：检查自动挡、22:00 前到酒店、锁定项、费用单位及引用的一致性；未知值不能当作通过。
5. **修改与版本**：先生成影响清单和候选变更，确认后再写入新版本；失败时保留原版本。
6. **输出与验收**：所有视图引用同一旅行版本；先用模拟数据验证规划逻辑，再单独验证真实工具及其降级行为。

顺序为建议，不将 P1 或后续网站功能设为 V1 完成前提。是否能提供可打开的路线入口、真实数据或导出格式，依赖实际环境与工具验证。

## 2. 建议的项目边界

| 内容 | 推荐处理方式 |
| --- | --- |
| Skill 指令及通用规则 | 放在仓库中，避免写死具体平台能力。 |
| 通用数据结构和测试样例 | 可进入公开仓库；使用虚构地点和无个人识别信息的数据。 |
| 个人长期偏好、行程、预订和支出 | 存放在用户授权的私有位置，不作为公开仓库默认提交内容。 |
| 健康信息、证件、密码和令牌 | 不写入普通旅行数据、样例或公开仓库；按正式规格进行隔离和最小化处理。 |
| 外部查询与文件导出 | 通过可替换的能力接口接入；工具或权限不可用时说明并降级。 |

建议在实施时加入忽略规则并检查提交内容，但忽略规则不能替代提交前检查，已提交过的敏感信息也不会因此自动消失。云端 Codex 中的工作目录不应默认视为永久或私有存储，具体持久化和访问权限需按实际环境验证。

## 3. 补充判定建议

- **入住时间**：22:00 是排他的上限；预计 22:00 或更晚都不满足。路线耗时无法核实时应标为未知，不得宣称通过。用户如需本次放宽，须明确确认并记录适用范围。
- **价格**：分别保存币种、单位、适用人数/房间及日期、费用构成、来源和查询时间。缺失项保持未知；已知小计可展示，但不能作为已核实的完整总价。押金与预授权单列，不计作已发生消费。
- **状态与锁定**：被选中、被锁定、已预订、已支付是不同事实。没有可靠确认时不提升预订状态；第三方订单并不会因为本地计划修改而被更改。
- **偏好覆盖**：一次性要求只进入本次旅行；长期偏好更新应逐项展示新旧值和影响，用户确认后保存。
- **冲突与回滚**：局部修改需分析交通、预算、跨日行程和预订依赖；变更会影响锁定项时先展示影响并取得确认，校验失败则保留原有效版本。
- **证据与地图**：说明数据来源、查询时间和适用条件；导航入口的存在不代表路径耗时或可通行性已验证。无法生成入口时明确缺失，而非伪造链接。
- **日期**：以旅行所在地时区解析相对日期；解析依据或范围不明确时询问。保存明确日期，不把“下周末”等相对表述当作永久日期。

## 4. 需要后续明确的问题

以下不是对冻结需求的修改；实施时应记录决定并通过版本管理：

1. **方案确认的最低条件**：哪些未知项会阻止确认，哪些可以接受为待核实？特别是无法核实 22:00 前抵达时，应区分“方案草稿可继续”与“硬约束已通过”。
2. **跨日与中转住宿**：夜间高铁、夜宿交通工具或连续驾驶跨午夜时，酒店抵达规则如何适用？在得到明确决定前不得擅自豁免。
3. **行程影响范围**：AC-20 要求其他天保持不变，AC-21 要求更新依赖数据；如果修改第二天会影响第三天的起点或预算，应展示影响，涉及锁定项时取得确认，而不是静默改写。
4. **报价状态与证据等级**：正式规格中的 `unknown / queried / rechecked / reference / expired / unavailable` 如何映射到具体字段、过期规则和费用总计，需在详细设计中确定；`queried` 不等于库存保证。
5. **修订与历史**：版本 ID、并发修改冲突、存储路径、恢复流程及数据迁移机制尚未选型；须满足不覆盖唯一有效历史版本的要求。
6. **权限边界**：仓库是公开的；个人旅行数据的实际私有存放位置、云端持久性与访问控制须在实现前验证。未来网站的双人身份验证和撤销访问需独立设计与测试。
7. **执行版的当前位置**：展示“当前下一站”需要用户提供进度或明确选择，不能推断实时位置；实时追踪不属于 V1。
8. **验收与优先级**：AC-25、AC-28 分别对应按需导出和未来网站；应在相应功能交付时验收，不能作为已经实现的证明。

## 5. 验证记录模板

每项外部能力单独记录：能力名称、测试日期与环境、输入条件、真实返回结果及来源、可用范围、费用/授权、时效、失败方式、降级策略、结果（通过 / 部分通过 / 未通过 / 未测试）。不要记录账号密码、令牌、证件或完整订单凭证。模拟数据的测试结果必须标为模拟，不得作为真实查询能力通过的证据。
